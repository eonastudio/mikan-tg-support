# Архитектура аддона tg-support

## Место в экосистеме mikan

mikan (≥ 0.5.1.0) запускает аддоны протокола 2 как соседние контейнеры (или внешние
процессы). Контракт — `PROTOCOL-v2.md` репозитория [getmikan/marketplace](https://github.com/getmikan/marketplace):

- **Хост** (`mikan`) ставит контейнер, выдаёт ему две пары токенов и переменные
  окружения: `MIKAN_ADAPTER_LISTEN`, `MIKAN_ADAPTER_TOKEN` (панель → аддон),
  `MIKAN_PANEL_URL`, `MIKAN_PANEL_TOKEN` (аддон → панель). Кастомный образ работает
  в bridge-сети `mikan-addons` (ICC выключен, порт опубликован только на loopback
  хоста, Panel API доступен через шлюз моста); контейнер: user 65532, rootfs
  read-only, `/tmp` tmpfs 16 МБ, cap_drop ALL, no-new-privileges, pids 64, память
  по `resources.mem_mb`.
- **Панель** хранит состояние аддона (KV в своей БД, с бэкапами), отдаёт события,
  проксирует админ-страницу аддона в sandboxed-iframe и его RPC-вызовы, ведёт аудит.
- **Аддон** не хранит файлов и не имеет своей БД: всё состояние — KV панели.

Ключевое решение: **аддон не занимает бот-слот панели** (permission `bot` — один
на панель, у официального бота mikan). Бот поддержки — собственный, со своим токеном
от @BotFather; аддон поллит `api.telegram.org` напрямую. Официальный бот (подписка,
оплаты) продолжает работать параллельно и не затрагивается.

## Хранилище (KV панели, permission `kv`)

Ключи `[A-Za-z0-9._:/-]{1,256}`, значение ≤ 64 КиБ, CAS через `If-Match: "<version>"`,
`if_absent` для дедупликации, TTL до 366 дней, квота аддона по умолчанию 256 МБ
(настройка панели `addons.kv_limit_mib`).

| Ключ | Содержимое |
|---|---|
| `cfg/main` | настройки: токен бота (секрет), API Telegram, приветствие, ИИ (base, ключ-секрет, модель, режим, задержка, язык, промпт, база знаний), срок хранения |
| `seq/tickets` | счётчик id тикетов (десятичное число, CAS) |
| `t/<id8>` | тикет: участники, тема, статус, счётчики (seq, msg_count, unread), last_from/last_msg_at, no_ai, last_chunk |
| `m/<id8>/<chunk4>` | чанки сообщений (≤ 48 КиБ или ≤ 200 шт. на чанк; ролловер CAS-идемпотентный) |
| `idx/tickets` | индекс: 300 свежих «голов» тикетов (список страницы), сортировка по updated_at |
| `ut/<tg_id>` | указатель на открытый тикет пользователя |
| `u/<tg_id>` | профиль клиента из событий панели (TTL 180 дней) |
| `ev/<id>` | дедуп-маркер события панели (TTL 8 дней — ретенション фида 7 дней) |
| `upd/<id>` | дедуп-маркер Telegram-update (TTL 48 ч) |
| `off/main` | подтверждённый offset getUpdates |

Записи через CAS с backoff (конкуренты: поллер и страница). Индекс — кэш: чинится
кнопкой «Перестроить индекс». Прун закрытых тикетов — каждые 6 ч и вручную.

## События панели (permission `events`)

Фид: `GET /panel/v2/events?types=…&limit=&wait=30` (long poll до 50 с), курсор хранит
панель, подтверждение — `POST /events/ack`. Доставка at-least-once → дедуп по `id`
(`ev/<id>` с `if_absent`). Подписаны на: `payment.paid`, `payment.refunded`,
`user.expiring`, `user.expired`, `traffic.90`, `traffic.100` (bot.*-события панель
отдаёт только держателю бот-слота — они не запрашиваются). Каждое событие сворачивается
в профиль `u/<tg_id>`; ретен션 фида панели — 7 дней, поэтому профиль накапливается
со временем жизни аддона.

## Админ-страница (permission `ui`)

- `/v2/info` отдаёт `ui.entry = /ui/index.html`; панель открывает страницу в iframe
  c `sandbox="allow-scripts"` и строгим CSP (`script-src 'self'` — поэтому JS во
  внешних файлах, без inline-скриптов и внешних CDN; `form-action 'none'` — поэтому
  кнопки вместо form-submit).
- Файлы: `GET /ui/<file>` из go:embed, с ETag/304, только безопасные заголовки.
- Данные: фрейм ↔ родительское окно `postMessage` (`{type:"rpc",id,method,path,body}` →
  `{type:"rpc-result",id,status,body}`), панель передаёт вызов дальше — в
  `POST /v2/ui/rpc` аддона с сессией админа (до 8 одновременных вызовов, не-GET —
  в аудит). Аддон отвечает своим HTTP-статусом и JSON ≤ 1 МБ.
- RPC-маршруты: `GET /bootstrap`, `GET /tickets?status=&q=`, `GET /tickets/{id}`,
  `POST /tickets/{id}/reply|close|reopen|draft|ai-send`, `DELETE /tickets/{id}`,
  `GET /tickets/{id}/media?seq=`, `GET|PUT /settings`, `POST /test/bot|/test/ai`,
  `POST /maintenance/reindex|/maintenance/prune`, `GET /status`.

## Бот (собственный Telegram-бот)

- Long poll `getUpdates(timeout=50, allowed_updates=[message])`; offset живёт в KV
  (`off/main`), при первом запуске backlog отклоняется (`offset=-1`).
- Дедупликация: маркер `upd/<update_id>` ставится **после** успешной обработки —
  сбой между обработкой и ack приводит к повтору, который движок гасит по
  `tg_msg_id` сообщения (идемпотентность на уровне хранилища).
- «Отравленный» update: после 3 неудач пропускается с записью в лог (очередь не встаёт).
- Ошибки: 429 → сон на `retry_after`; 409 → «another poller» (дубль токена) с ожиданием;
  401/403 → поллинг останавливается и ждёт нового токена из настроек; транспорт/5xx →
  backoff 2→60 с.
- Смена токена/API в настройках рестартует цикл без перезапуска контейнера
  (cfgw.OnChange → ApplyConfig, гонки закрытий/стартов — поколение цикла).

## Жизненный цикл тикета

```
пользователь: текст/фото/файл
   ├─ нет открытого тикета → CreateTicket (id из seq/tickets, subject=первая строка,
   │                          указатель ut/<tg_id>, первая запись в чанк 0, индекс)
   │                          → клиенту «🎫 Тикет #N создан»
   └─ есть → AppendMessage (seq++, unread++, last_from=user)
              └─ режим auto + ИИ готов + !no_ai → таймер на ai_delay
                    └─ по таймеру: тикет всё ещё ждёт (open, last_from=user)?
                          → контекст (профиль+история+знания) → LLM → повторная
                            проверка (агент мог ответить) → отправка → запись from=ai
агент (страница): reply → cancelAI → отправка в Telegram → запись from=support,
                  unread=0; ответ в закрытый тикет → reopen + уведомление клиента
/close (клиент) или кнопка «Закрыть» → статус closed, указатель ut снимается,
                  клиенту уведомление; новое сообщение клиента → новый тикет
лимит 5000 сообщений → авто-закрытие + продолжение в новом тикете
prune: закрытые старше retention_days (по умолч. 60) удаляются из KV
```

## Запуск и надёжность

- `main.go`: HTTP-сервер стартует **немедленно** (хост ждёт `/v2/info` ≤ 30 с),
  а Panel API в это окно установки может ещё отвечать 401 — все фоновые циклы
  (watcher конфига 15 с, поллер, evfeed, sweep 1 мин, prune 6 ч, self-check 30 с)
  переживают недоступность панели backoff'ами и догоняют состояние после.
- Graceful shutdown по SIGTERM/SIGINT: поллер сохраняет offset, сервер отдаёт
  текущие запросы (≤ 15 с).
- `/v2/info` всегда отвечает статикой — установка не ломается из-за недоступности KV.
- Идемпотентность: дедуп update'ов и событий, CAS-записи, seq-дедуп в чанках —
  повторная обработка после сбоев не двоит сообщения.

## Тесты

`go test ./...` — юнит и интеграция на фейках: `internal/paneltest` (фейк Panel API:
KV с версиями/TTL/CAS, события с курсором), фейк Bot API (очередь update'ов, запись
отправленных), фейк LLM. Покрыты: раскладки KV, конкурентные добавления (8×6 CAS),
ролловер чанков, дедупликация replay, prune/индекс/ребилд, профили из событий,
секреты в настройках (маскировка, сохранение при пустом значении), flood-контроль,
«позови человека», auto/draft-потоки ИИ, auth/401, ETag/304, traversal, валидация
RPC, лимиты медиа, 429/409/401 Telegram, SplitText, Sanitize, netguard (metadata IP).
